# Direct-rename lineage feasibility (#440)

## Question and method
Can existing SQLGlot recover conservative direct-column aliases from real dbt compiled SQL, without claiming expressions preserve documentation meaning? Scope is an offline probe, not a shipped resolver. No runtime/dependency changes or warehouse access. Owning issue: https://github.com/z3z1ma/dbt-osmosis/issues/440 (read 2026-11-16).

Reproduce with a Python environment already containing dbt-core, dbt-duckdb and SQLGlot:
`python .10x/research/lineage-440/experiment.py`
The script creates a temporary local DuckDB project, compiles five models with `dbt compile --no-introspect`, and probes the compiled_code strings. It deletes its temporary project on exit. The compiler subprocess has a 60-second timeout; SQLGlot itself is not time-bounded in this research probe. No persistent runtime cache or YAML mutation occurs. Recorded output is `lineage-440/results.json` relative to this record; it includes compiled SQL and exact versions (Core 1.10.20, DuckDB adapter 1.10.0, SQLGlot 30.8.0). Seven scenario status assertions and three identity/error assertions passed.

## Findings
- Qualified direct alias and CTE rename through stars resolve to one direct leaf when a complete schema is supplied.
- LOWER hidden inside a CTE still has one source leaf. Therefore leaf count alone is unsafe: every projection on the path must be checked for direct-column semantics.
- COALESCE across joined sources has two leaves and is rejected. An ambiguous unqualified joined column raises OptimizeError with qualification validation enabled.
- Missing-schema CTE star does **not** necessarily raise: observed a `*` placeholder leaf. Probe initially expected an exception-like outcome and failed; corrected the expected observation to rejection, preserving the no-candidate invariant. Reject placeholders explicitly.
- Missing compiled SQL is unavailable. The issue's assertion that compiled SQL is already available is not universally true.
- These are candidate column identities, not validated dbt donors. SQLGlot leaf names contain query aliases (`s.old_name`), not dbt unique_ids. The leaf Table expression and quoted/catalog/schema-aware relation index must resolve to exactly one eligible ancestor before inheritance.

## Source and architectural evidence
Primary sources checked 2026-11-16: https://sqlglot.com/sqlglot/lineage.html documents schema/dialect/source inputs; the installed 30.8.0 API was exercised rather than assuming current online API equivalence. https://docs.getdbt.com/reference/artifacts/manifest-json documents that compiled SQL may be absent; inspect actual compiled_code in Python artifacts.

At main 9a92d861, `core/inheritance.py:_process_inherited_column` uses `_find_matching_column` and `_build_graph_edge`; `_build_graph_edge` passes `name` to `_get_unrendered`. A rename resolver must preserve **both target and donor column identities**: target for settings, donor for YAML/doc-block retrieval. Reusing target-name lookup silently defeats unrendered docs. `_should_drop_graph_description`, graph merging and the explicit progenitor override pass govern existing description precedence and must remain authoritative. The probe neither exercises nor certifies those mutation paths.

## Conclusion, limits and next action
Direct aliases are feasible without another dependency. Do not ship generic single-leaf inheritance or transformed-column copying. This probe is DuckDB-only and does not establish Trino quoting, adapter mapping, unions, ephemeral-model inlining, recursive CTEs, permissions or performance. No docglow source was copied; its licensing claims were not verified or relied upon.

Next owner: `.10x/specs/direct-rename-lineage.md` (draft). Before runtime implementation, resolve the fallback conflict (legacy name matching can still select an unrelated same-name donor after lineage rejects ambiguity), measured resource bounds, supported dialect/adapter scope and relation-to-node ambiguity policy. Test actual docs-block preservation, explicit descriptions, force/override controls, dry-run/idempotence and caches through the existing pipeline. A compiled-SQL hash alone is insufficient cache identity: schema, dialect, relation-to-node mapping, manifest generation and resolver version also matter. Do not cache final descriptions; they can change independently of SQL.
